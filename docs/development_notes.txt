FIREWATCH 69 — DEVELOPMENT NOTES
================================

Project:
An Integrated Real-Time Fire Incident Reporting and High-Risk Area Analytics System for Barangay 69, Tondo, Manila.

Proposed stack:
- Language: mostly JavaScript (ES modules) on web and API; TypeScript is not planned.
- Web: ReactJS + JavaScript (ES modules) + Vite
- API: Node.js + ExpressJS (JavaScript, ES modules)
- Mobile: Flutter + Dart
- Database: MongoDB + Mongoose
- Real-time: Socket.IO
- Maps: Mapbox (confirm Flutter/web SDK needs and pricing before finalizing)
- Push notifications: Firebase Cloud Messaging (FCM)
- API testing: Postman
- Version control: Git + GitHub

Architecture principles:
1. All clients use the same backend API and central database.
2. Enforce authorization in the API; frontend visibility alone is not security.
3. Use Mongoose schemas, validation, indexes, and references where useful.
4. Use GeoJSON Point coordinates in [longitude, latitude] order and 2dsphere indexes for proximity queries.
5. Keep media files outside MongoDB; store metadata and secure storage references.
6. Preserve incident and assignment history through append-only events.
7. Treat Socket.IO as a live update channel, not the permanent source of truth.
8. Validate incident workflow, severity rules, blotter requirements, and organizational permissions with the barangay/BFP.
9. Build a minimal end-to-end incident workflow before implementing every module.
10. Never represent unverified hydrant status, evacuation availability, or risk factors as confirmed facts.

Suggested repository layout:
- client/              React web app (officials)
- mobile/

  - responder_mobile/  Flutter — emergency responder

Development approach (summary):
Across the project, delivery follows four layers. Repeat steps 1–3 per feature slice (auth, incidents, etc.):

  Layer A — Server first (server/)
  Layer B — Client UIs with mock data (client/, resident_mobile, responder_mobile)
  Layer C — Integrate all three clients with the FireWatch API (same MongoDB-backed Express app)
  Layer D — Integrate external services (maps, push, media storage, email) when those features ship

Layer A — Backend first (per slice)
- Implement Mongoose models, validators, routes, and controllers under /api/v1.
- Add automated API integration tests (server/tests/).
- Authorization and business rules live only on the API.
- MongoDB is required infrastructure for the API from Phase 1 onward (local or hosted).

Layer B — Basic CRUD UIs with mock data (no live API yet for that slice)
- client/ (officials web): list/create/read/update/delete flows, routing, loading/empty/error states.
  Use fixtures/mocks that match the API response shape (e.g. client/src/mocks/ or a service layer
  with mock and real implementations). Dev flag: VITE_USE_MOCK (and VITE_API_URL when integrating).
- mobile/resident_mobile: same pattern — mock repositories / local JSON; resident + guest flows (features.txt C + D).
- mobile/responder_mobile: same pattern; responder flows (features.txt B).
- “CRUD” here means UI and client-side state against sample data, not HTTP to the server yet.

Layer C — Integrate client + both mobile apps with the server
- Point all three apps at the API base URL; JWT login, secure token storage, CORS (WEB_ORIGIN).
- Swap mock services for HTTP clients slice by slice; keep mocks behind a flag for demos if useful.
- Do not treat hidden UI as security; mirror server permissions for display only.
- A slice is demo-ready on the API only after Layer C for that slice (or explicit API-only E2E tests).

Layer D — External APIs and services (later; mostly Phase 6+)
- Integrate after Layer C for the related product feature, not before wiring clients to Express:
  Mapbox (web/Flutter public tokens), Firebase/FCM (push), object storage (attachments),
  optional email provider, enhanced Socket.IO rooms (live updates; MongoDB remains source of truth).
- UI may use placeholder maps/notifications until Layer D; backend incident/auth data uses Layer A/C.

Deliver backend + tests (Layer A) before relying on mock UI (Layer B) for the same slice.
Finish Layer C before moving to the next slice. Layer D is phased (see phases.txt Phase 6).

Development conventions:
- Use environment variables for secrets and service URLs.
- Add linting/formatting and consistent error responses.
- Use database migrations/seed scripts or versioned seed data as appropriate.
- Add automated tests for authentication, permissions, incident transitions, and location endpoints.
- Keep separate development, test, and production environments.
